# v1_explore —— 缓存分块调参 & 大矩阵实验总结

**动机**：正文 §3.2 说「v1 缓存分块是负优化」。但两个疑问值得实测：
1. 调块大小（BS）能不能翻盘小场景的劣势？
2. 换成 **L2 装不下** 的大矩阵（B > 16MB），分块是不是就该赢了？

**方法**：单线程，对比几种循环组织（源码 `v1_explore.cpp`）：

| 名称 | 做法 |
|---|---|
| `ikj` | 无分块，内层 `j` 跑满整行 N |
| `v1_bsX` | 原始 v1：`i/k/j` 三层都按 BS 分块（**内层 j 被切短到 BS**） |
| `blk_k256` | 只分块 `k`(KC=256)，内层 `j` 跑满：B 的 KC×N 面板留 cache、被所有行复用 |
| `blk_ik` | 分块 `i`(MC=128)+`k`(KC=256)，内层 `j` 跑满 |

编译：`clang++ -O3 -mcpu=apple-m4 -ffast-math -funroll-loops`。机器：M4 Pro，L2=16MB。

---

## 实测结果（GFLOPS，单线程）

| kernel | N=1024 (B=4MB, ≤L2) | N=2048 (B=17MB, >L2) | N=4096 (B=67MB, ≫L2) |
|---|---|---|---|
| **ikj** | **32.7** | **32.6** | **31.5** |
| v1_bs32 | 18.1 | 16.1 | 10.2 |
| v1_bs64 | 21.7 | 19.3 | 16.3 |
| v1_bs128 | 26.3 | 22.1 | 21.5 |
| v1_bs256 | 29.3 | 26.7 | 25.6 |
| blk_k256 | 33.0 | 32.5 | 32.4 |
| blk_ik | 32.7 | 32.6 | 32.2 |

（N=6144 单线程太慢只跑到一半，趋势与 4096 一致：ikj 31.4，v1_bs* 仍全面落后。）

---

## 三个结论

### 1. 调 BS 不能翻盘：BS 越大越接近 ikj，但永远追不上
`v1_bs32 → bs256` 一路变快（18→29 @1024），因为块越大、内层 `j` 越长、向量化损失越小。
但即便 BS=256 仍 < ikj。**只要还在切内层 `j`，就有短循环惩罚**，追平就到头了。

### 2. 大矩阵没有让分块翻盘：ikj 在 B≫L2 时几乎不掉速
反直觉——N=4096 时 B=67MB 远超 16MB L2，按「B 被反复从 DRAM 重读 N 次」的想象，
ikj 该崩。但它稳在 ~31.5 GFLOPS。原因：单线程**顺序流式**访问 B + 硬件预取，
Apple 的高带宽统一内存能喂上；而且单核本就跑不满全内存带宽。

### 3. 减少 DRAM 流量也没用 → 真正的瓶颈是内层循环，不是 cache
`blk_k256` 让 B 只从 DRAM 读一次（流量降约 100×），可速度和 ikj **一模一样(32)**。
这证明：**ikj 家族的瓶颈是内层 `C[i][j] += a*B[k][j]` 的「访存:计算 = 3:1」**
（读 C + 读 B + 写 C 对 1 次 FMA），即使数据全在 L1，load/store 端口也把吞吐卡在 ~32 GFLOPS。
cache 分块只动「数据在哪一级」，动不了这个比例。

---

## 总的教训

> **单线程 GEMM 的 ~32 GFLOPS 天花板由内层循环的访存:计算比决定，不是 cache/DRAM。
> 纯缓存分块（不管怎么调参、不管矩阵多大）都突破不了它。
> 要突破必须换内层循环——用寄存器分块把比例从 3:1 砍到 0.25:1，也就是 v2（32 → 110）。**

这也解释了为什么正文里 v1 是「负优化的教训」：它在一个**内层受限**的问题上做**cache 级**的优化，
方向就错了；还顺带切碎内层循环、增加 C 的中间搬运，于是比什么都不做的 ikj 还慢。

运行：`clang++ -std=c++17 -O3 -mcpu=apple-m4 -ffast-math -funroll-loops v1_explore.cpp -o v1_explore && ./v1_explore`
