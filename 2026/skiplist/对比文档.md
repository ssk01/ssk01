# Skiplist 实现对比：Redis vs 手写版

对比对象：

| 版本 | 文件 | 说明 |
|------|------|------|
| Redis 版 | `benchmark/redis_zskiplist.h` | 从 Redis 7.x `src/t_zset.c` 移植（sds→std::string，zmalloc→new/free），算法/结构不变 |
| 手写版 | `skiplist.cpp` | 用户手写，int key → int value |

---

## 1. 数据结构

### Redis 版

```cpp
typedef struct zskiplistNode {
    std::string ele;             // 元素（字符串）
    double score;                // 分数（主排序键）
    struct zskiplistNode *backward;   // 指向前一个节点（level 0）
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;      // 跨过多少个节点（用于 rank 计算）
    } level[];                   // 柔性数组，level 0..31
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;
    unsigned long length;
    int level;                   // 当前最高层数
} zskiplist;
```

- **双键排序**：(score, ele)。先比 score，score 相同再比 ele 字符串。
- 每个 level 都带 `span`：当前节点到 forward 之间隔了多少个节点。这是实现 O(log n) `zslGetRank` / `zslGetElementByRank` 的关键。
- `backward` 指针支持反向遍历（ZREVRANGE 用）。
- `header` 是哑节点（32 层），`tail` 指向最后一个真实节点。

### 手写版

```cpp
struct Element {
    Element** next;   // 每层指向下一节点
    int value;
    int key;          // 唯一
    int level;
};

class Skiplist {
    int max_level_;
    Element* head_;   // INT_MIN 哑节点
    Element* tail_;   // INT_MAX 哑节点
};
```

- **单键排序**：int key。无 span、无 backward。
- 首尾都是哑节点（INT_MIN / INT_MAX），每个节点 `next[]` 定长分配 `level` 个。
- 构造时把 head 的所有层直接指向 tail（`head_->set_next(tail_, i)`）。

## 2. 关键算法对比

### 随机层高

| | Redis | 手写版 |
|--|-------|--------|
| P 值 | 0.25 | 0.5（`rand()%2==0` 就升一层） |
| 概率分布 | 几何分布 P=1/4 | 几何分布 P=1/2 |

手写版 P=0.5 意味着**层数平均更高**（期望层数 2 vs Redis 的 4/3），节点更"胖"，内存更大、cache 更差。基准里用的是 `Skiplist(32)`。

### 插入

Redis `zslInsert`：O(log n)，逐层记 `update[]` 和 `rank[]`，边找边维护 span。

手写版 `insert`：同样逐层找 lower_bound，记录 `prev[]` / `next[]`，找到同 key 则原地更新 value。**没有维护 span，因为不需要 rank 查询。**

### 查找

| | Redis | 手写版 |
|--|-------|--------|
| 按 key 找 | 需同时提供 (score, ele) | `get(key)` |
| 按 rank 找 | `zslGetElementByRank` O(log n) | ❌ 无 |
| 查 rank | `zslGetRank` O(log n) | ❌ 无 |

手写版查找逻辑和 Redis 几乎一样（高层跳过、底层精查），只是少比较一项，且没有 rank 能力。

### 更新

- Redis `zslUpdateScore`：先判断新 score 若仍在原位则只改 score（快路径），否则删了重插。
- 手写版：无 updateScore，`insert` 遇到同 key 直接覆盖 value。测试里"update"就是重复 insert。

### 删除

- Redis `zslDelete`：O(log n)，逐层 unlink + 收拢 span。
- 手写版：**未实现**（用户稍后补）。

### 插入时的前驱/后继存储（update[]/prev[]）

Redis 和手写版插入时都要先逐层记录前驱/后继，**概念完全一样**（Redis 的 `update[]` 就是手写版的 `prev[]`），但存储方式不同：

| | Redis | 手写版 |
|--|-------|--------|
| 数组 | `update[ZSKIPLIST_MAXLEVEL]` + `rank[ZSKIPLIST_MAXLEVEL]` | `vector<Element*> prev/next` |
| 长度 | 固定 32（`#define ZSKIPLIST_MAXLEVEL 32`） | 动态 = new_level |
| 分配 | **栈上定长数组，零堆分配** | 每次 insert 构造 vector → **2 次堆分配** |
| 额外信息 | `rank[]` 存每层累计跨度（算 span 用） | 无（没有 span） |

Redis 源码（`redis_zskiplist.h:107-108`）：
```c
zskiplistNode *update[ZSKIPLIST_MAXLEVEL];   // 栈上，32 个
unsigned long rank[ZSKIPLIST_MAXLEVEL];      // 栈上，32 个
```
手写版（`skiplist.cpp:61-64`）：
```cpp
vector<Element*> prev(new_level, nullptr);   // 堆上，每次 insert 都 new
vector<Element*> next(new_level, nullptr);
```

差异要点：
- Redis 固定开 32 长度，虽然大部分层用不到，但数组在栈上、随函数返回自动销毁，不污染 cache、无分配成本。
- 手写版按实际层数 `new_level` 开 vector，看似更省，实际是堆分配 + 无意义，插入性能被拖累。
- 手写版没有 span，所以不需要 `rank[]`——代价是没有 O(log n) rank 查询能力。

### 范围查询

- Redis `zslFirstInRange` / `zslNthInRange`：按 score 区间，O(log n + m)。
- 手写版：无。按 key 的范围查询同理也能做（从 head 找 lower_bound 后顺序走 level 0），但未实现。

## 3. 性能对比（200k 元素，实测）

### Int 键（两种 skiplist 均可参与，最公平）

| 操作 | 手写版 | std::map<int,int> | unordered_map<int,int> |
|------|--------|-------------------|------------------------|
| insert | 73.4 ms | 28.0 ms | 2.7 ms |
| find | 67.5 ms | 20.2 ms | 2.6 ms |
| update | 86.0 ms | 225.7 ms | 3.4 ms |

手写版比 std::map 慢 2~3 倍。可能原因：
1. P=0.5 层数高 → 每节点 `next[]` 额外 new 一块数组，**每节点 2 次堆分配**（节点本体 + next 数组），cache 差。
2. `get`/`insert` 用 `std::tie(lhs, rhs) = find_lower_bound(...)`，返回 pair + 多次解引用，编译器未必全内联。
3. `insert` 里 `vector<Element*> prev/next` 每次插入都构造 → 又 2 次堆分配。

### String 键 + double score（仅 Redis 版，与手写版不直接可比）

| 操作 | Redis 版 | std::map | unordered_map |
|------|----------|----------|---------------|
| insert | 64.1 ms | 54.1 ms | 9.0 ms |
| find | 151.5 ms | 105.1 ms | 13.9 ms |
| update | 176.1 ms | 189.3 ms | 12.0 ms |
| range | **79.9 ms** | 157.6 ms | 129.0 ms |
| delete | 134.3 ms | 103.2 ms | 28.2 ms |

Redis 版慢在手写版之上还要比 string + double；它唯一明显胜出的是 **score 范围查询**（map/unordered_map 无 score 索引只能全扫）。这正是 zset 里 skiplist 存在的意义：配合 dict 做 O(1) 点查 + O(log n) 范围/rank 查询。

> 注意：上面两组数字来自不同基准（键类型不同），**不能跨组直接比**。要公平对比 Redis 版 vs 手写版，应让手写版也支持 int key 范围/rank，或让 Redis 版用 int score 跑同样负载。

---

## 4. 结论 / 待办

**手写版 vs Redis 版，主要缺：**
1. `delete`（用户即将实现）
2. `span` → rank 查询（`zslGetRank` / `zslGetElementByRank`）
3. `backward` → 反向遍历
4. score/range 查询（若要做成 zset 语义）
5. 把 `Element::next` 改成柔性数组或统一分配，减少堆分配

**性能上**：手写版目前找/插比 std::map 慢 2~3 倍，比 unordered_map 慢一个量级，这是 skiplist 的结构性代价；但 find 比 Redis 版快（因为 int vs string+double 的比较成本）。范围/rank 查询的 skiplist 优势还没在手写版上体现出来，等 delete + rank 补上后可同台完整对比。
