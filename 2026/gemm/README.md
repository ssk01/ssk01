# 从 naive 到打败 OpenMP：单精度 GEMM 优化实录

在 Apple M4 Pro（arm64，14 核）上，从最朴素的三重循环出发，一步步优化单精度矩阵乘法
`C = A × B`（row-major，方阵），最终用 **v3** 稳定跑到 OpenMP 朴素并行版的 **~3 倍**。

代码全部在 `gemm.cpp`，一键构建见 `Makefile`。

---

## 1. 目标与基准

- 被优化对象：`C[N][N] = A[N][N] × B[N][N]`，`float`(fp32)。
- 竞品：一份「正常人会写」的 OpenMP 并行版（`#pragma omp parallel for` + 缓存友好的 i-k-j 循环，14 线程）。
- 要求：做出 3 个逐步优化的版本，直到快过 OpenMP。
- 指标：`GFLOPS = 2·N³ / 时间`，以及相对 OpenMP 的加速比。

---

## 2. 环境准备（踩坑记录）

本机是 arm64 的 M4 Pro，但系统里的 Homebrew 是 **x86_64（Rosetta）** 版，带来的 `gcc`、`libomp`
都是 x86_64 的。若直接用，OpenMP 竞品会跑在 Rosetta 翻译层上，对比不公平。

解决：直接抓 Homebrew 的 **原生 arm64 `libomp` bottle**，解包到 `third_party/libomp/`，
让 Apple `clang` 走 `-Xpreprocessor -fopenmp` 原生链接。

一个关键坑：用 `install_name_tool` 改了 dylib 的 install name 后，**代码签名失效**，
arm64 macOS 会在加载时直接 `SIGKILL`（程序无任何输出、退出码 137）。修复：

```sh
codesign -f -s - third_party/libomp/lib/libomp.dylib
```

（ad-hoc 重签即可。主程序 clang 会自动 ad-hoc 签名。）

## 3. 各版本一览

| 版本 | 线程 | 核心手法 | 位置 |
|---|---|---|---|

| `naive_t` | 1  | 转置 B 修复列访问（行列缓存优化） | `gemm_naive_t` |
| `ikj`     | 1  | i-k-j 循环重排（改下标），无 OpenMP | `gemm_ikj` |
| `openmp`  | 14 | 同 `ikj` 循环 + `parallel for`（竞品） | `gemm_openmp` |
| `v1`      | 1  | 缓存分块 + i-k-j 重排 | `gemm_v1` |
| `v2`      | 1  | NEON 8×8 寄存器微内核 + A/B 打包 | `gemm_v2` |
| `v3`      | 14 | v2 + 按行条带多线程 | `gemm_v3` |
| `cblas`   | 多 | Apple Accelerate `cblas_sgemm`（AMX 矩阵协处理器）参考 | `gemm_cblas` |

### 3.0 naive —— 最朴素基准

```c
for i: for j: { s=0; for k: s += A[i*N+k]*B[k*N+j]; C[i*N+j]=s; }
```

慢在两点：

1. **列访问 B**：内层沿 `k` 走 `B[k*N+j]`，每次跨一整行，cache 几乎每次 miss。
2. 无向量化、无并行。

N≥1024 时列访问要几十秒，所以基准里只在 N≤512 跑它，大尺寸直接标 `-`。

### 3.0b naive_t —— 行列缓存优化（转置 B）

naive 唯一的大问题就是列访问 B。最小改动：先把 B **转置**成 `Bᵀ`，
内层点积 `s += A[i][k] * Bᵀ[j][k]` 对两个操作数都变成**按行连续**访问，
cache 命中大幅改善、编译器也能把它向量化成规约（reduction）：

```c
for k,j: Bt[j*N+k] = B[k*N+j];          // O(N²) 转置，相对 O(N³) 可忽略
for i: for j: { s=0; for k: s += A[i*N+k]*Bt[j*N+k]; C[i*N+j]=s; }
```

仅此一步（仍是单线程、无手工 SIMD），吞吐从 naive 的 ~2 GFLOPS 跳到 **~37 GFLOPS（≈18×）**，
甚至比后面 v1 的分块版还快——说明「修复访存模式」往往比「加分块」收益更直接。

### 3.1 竞品 openmp —— 「正常写法」的并行版

两处改动就让它比 naive 快上百倍：

1. **循环重排 i-k-j（改下标）**：把 `k` 提到 `j` 外面，内层变成
   `C[i][j] += a * B[k][j]`，`B` 和 `C` 都按行连续访问 → cache 友好 + 编译器自动向量化。
2. `#pragma omp parallel for` 把 `i` 行分给 14 个核。

这是一个**很强**的基准（250~274 GFLOPS），也是要打败的目标。

> **`ikj`（无 OpenMP 版本）**：和 openmp 完全相同的 i-k-j 循环体，但**去掉 `parallel for`、单线程**。
> 实测 ~32 GFLOPS，而 openmp ~260 GFLOPS——两者相除正好说明 openmp 的提速主要来自
> **14 线程并行（约 8×）**，循环重排本身（naive 2 → ikj 32，约 16×）则来自访存模式修复。
> 有意思的是 `ikj`(32) 和 `naive_t`(37) 量级相当：i-k-j 重排 与 转置 B 是解决同一个「B 列访问」问题的两条路。

### 3.2 v1 —— 单线程缓存分块（一个「负优化」的教训）

在 i-k-j 基础上做 `64×64` 三层分块（`ii/kk/jj`），本意是让活跃数据留在 L1/L2。
但实测 **v1（~20 GFLOPS）反而慢于 plain ikj（~32 GFLOPS）**。原因值得记下——
**分块用错了场景就是负优化**：

1. **它要解决的问题在这个规模下不存在。**
   分块的意义是「省 DRAM 流量」。但 N=1024 时 B 才 4MB、N=2048 才 16MB，正好落在
   **16MB 共享 L2** 里。plain ikj 每行 i 扫一遍整个 B，其实是从 **L2** 流出来的，不是 DRAM。
   省 DRAM 的收益 ≈ 0。

2. **内层循环被切短 → 向量化效率掉。**
   ikj 内层 `for j` 跑满整行 N（连续、又长的向量流）；v1 里 `for j` 只在 `jj` 块内跑 **64 步**。
   短循环让循环控制/尾部余数/预取热身的占比上升，稳态吞吐下降。

3. **对 K 分块（`kk`）反而给 C 增加了访存流量。**
   v1 的嵌套是 `ii→kk→jj→i→k→j`：同一个 C 块 `(ii,jj)` 在**每个 kk 块都要被读-改-写一遍**。
   两次访问之间会扫过整条 ii 行带（64×N×4 ≈ 256KB > 128KB L1）把它挤出 L1，
   于是每个 kk 都要把 C 从 L2 重新搬进搬出，共 N/64 次。
   而 plain ikj 对固定 i **一次性扫完所有 k**，那一行 C（4–8KB）全程驻 L1，只过一遍、零重复搬运。

**根因**：ikj 和 v1 都没有寄存器级复用（AI≈0.5，都是 load-bound）。v1 唯一的理论优势是 B 复用，
但 B 从 L2 出来本就便宜、省不下什么；它的三项额外开销却是实打实的。所以 v1 慢过 ikj。
> 教训：**分块必须配上寄存器微内核（把复用做进寄存器）才有意义**——单纯为分块而分块，
> 在 load-bound 场景只会切碎循环、增加中间结果搬运。这正是 v2 要补上的。

### 3.3 v2 —— NEON 微内核 + 打包（单核逼近峰值）

这是单核性能的关键跃迁（21 → 111 GFLOPS）。核心是一句话：
**别再让内层循环反复读写内存里的 C——把 8×8 一小块 C 全塞进寄存器里累加，算完了才写回内存一次。**

下面分「打包 → 累加 → 回写」三步画图讲清楚。

#### 步骤 1：打包（pack）——把要用的数据揉成微内核顺序连续的样子

微内核每一步 k 需要「A 的 8 个行值」和「B 的 8 个列值」。但它们在原矩阵里是
带 stride 的（隔一整行才有下一个），直接读 cache 命中差。所以先重排成**连续小条**：

```
 pack_A：取 A 的 8 行 × kc 列，转置成「每个 k 一组连续 8 个行值」

   原始 A(row-major)              Apack(连续)
        k0 k1 k2 …                 [k0]: a0 a1 a2 a3 a4 a5 a6 a7
   r0 │ ·  ·  ·                    [k1]: a0 a1 a2 a3 a4 a5 a6 a7
   r1 │ ·  ·  ·          ──►       [k2]: a0 a1 a2 a3 a4 a5 a6 a7
   …  │            (8行×kc)         …      (微内核顺时针流式读, 0 stride)
   r7 │ ·  ·  ·

 pack_B：取 B 的 kc 行 × 8 列，「每个 k 一组连续 8 个列值」

   原始 B(row-major)              Bpack(连续)
        c0 c1 … c7                 [k0]: b0 b1 b2 b3 b4 b5 b6 b7
   k0 │ ·  ·  ·                    [k1]: b0 b1 b2 b3 b4 b5 b6 b7
   k1 │ ·  ·  ·          ──►       …
   …  │            (kc×8列)
```

#### 步骤 2：累加（accumulate）——每一步 k 做一次 8×8 外积，加到寄存器

> **什么是「外积累加」？** 外积 = 一个列向量 `a`(8×1) 乘一个行向量 `b`(1×8)，得到 8×8 矩阵，
> 第 `[i][j]` 格 = `a[i]·b[j]`。矩阵乘法有个恒等式：
> `C = A×B = Σ_k (A 的第 k 列) ⊗ (B 的第 k 行)`。
> 所以整块 8×8 tile = 把「每个 k 的外积」累加起来。
> 这跟 naive 的**内积/点积**视角相反：naive 一次只算 1 个 C 元素（A 一行·B 一列求和）、2 个载入只做 1 个 madd；
> 外积则一次更新整块 8×8、16 个载入做 64 个 madd（每个 `a` 用 8 次、每个 `b` 用 8 次）——这就是复用的来源。
> AMX/Tensor core 的硬件本质也是「一条指令做一个外积/小矩阵乘」。

> **「算一个 C[i][j] 不就是 K 次累加吗？为什么是 64 次不是 8 次？」**
> 没错，一个 `C[i][j]` 就是 K 次乘加。但微内核一次算的是**整块 8×8 = 64 个** `C[i][j]`，
> 每个都要 K 次，所以这块总乘加数 = `64×K`——这是死的。「64 per k」和「K per element」
> 只是**同一堆 `64×K` 次乘加换了循环顺序**，不是多算：
>
> ```
> 按元素(点积): for (i,j) in 64: for k in K: C[i][j]+=a·b   ← 先把一个元素的 K 次做完
> 按 k  (外积): for k in K: for (i,j) in 64: C[i][j]+=a[i]·b[j] ← 每个 k 给全部 64 个各加一笔
> 两者总乘加都是 64×K, 一模一样
> ```
>
> 换成「按 k」是为了**省 load 不是省乘加**。同样 `64×K` 次乘加，两种顺序的访存差 8 倍：
>
> | 顺序 | 乘加 | 载入 | 每次乘加载入 |
> |---|---|---|---|
> | 按元素(点积) | 64K | **128K**（每个元素各读自己的 A 行/B 列，行列被重复读 8 次） | 2 |
> | 按 k(外积) | 64K | **16K**（每个 k 只读 8 个 a+8 个 b，喂给全部 64 个元素） | 0.25 |
>
> 按 k 时：一个 k 上读一次 8 个 a、8 个 b，就地喂给这 64 个元素（`a[i]` 配 8 个 b、`b[j]` 配 8 个 a）。
> **乘加数没变，访存降了 8 倍**——这就是从「访存受限」翻到「算力受限」的原因（瓶颈本在 load）。

第 k 步：读进 A 的一列(8 个 `a`) 和 B 的一行(8 个 `b`)，做**外积**（每个 a 乘每个 b），
把 64 个乘积**分别累加**到 64 个寄存器累加器上。C 不碰内存：

```
 第 k 步的外积：  C_acc[i][j] += a_i * b_j
                                                     ← Bpack[k] : b0 b1 b2 b3 b4 b5 b6 b7
          ┌───────────────────────────────────────────────────
      a0  │ +a0·b0  +a0·b1  +a0·b2  ……              +a0·b7
      a1  │ +a1·b0  +a1·b1                           +a1·b7
      a2  │ +a2·b0                                   +a2·b7      每个格子 = 一个寄存器累加器
 Apack[k] a3  │ …                                    …           (共 8×8 = 64 个, 全程不落内存)
   ↑  a4  │
      a5  │
      a6  │
      a7  │ +a7·b0                              …    +a7·b7
          └───────────────────────────────────────────────────

 向量化实现：8 列拆成 2 个 float32x4（b0..3 / b4..7），
 每行用 vfmaq_laneq 把某个 a_i 广播乘上去 → 每步 16 条向量 FMA。
 64 个累加器 = 16 个 float32x4 寄存器（8 行 × 2 个半宽），NEON 有 32 个寄存器放得下。
```

#### 步骤 3：回写（write-back）——kc 步全加完，一次性写回 C

```
   k=0        k=1              k=kc-1
  ┌────┐    ┌────┐            ┌────┐        ┌──────────┐        C[i..i+8][j..j+8]
  │外积│ +  │外积│ + …… +     │外积│   =    │ C_acc 8×8│  ──►   += C_acc
  └────┘    └────┘            └────┘        └──────────┘        16 load + 16 store
  (寄存器)  (寄存器)          (寄存器)       (仍在寄存器)        每行读 C→加 accum→写回
```

[重要] **「只写一次」不是指只写 1 个 float —— 该写的 64 个 float 一个不少。** 省的是**中间**那 kc-1 次反复读写同一个 8×8 tile：

```
ikj 算同一个 8×8 tile:  每个 k 步读 C 64 次 + 加 + 写 C 64 次
                         kc=256 时 → 64×256 = 16384 次读 + 16384 次写 全砸在 C 上

micro_8x8 算同一个 tile:  第 0..255 步: 0 次读写 C（全在寄存器里攒）
                          最后:       读 C 64 次 + 写 C 64 次   (16 load + 16 store 指令)
                                      省掉中间 255 批 = 256 倍
```

对比 ikj：ikj 内层每算一个数就 `读C→加→写C` 一次（3:1 的访存:计算）；
微内核把整块 C 留在寄存器，kc 步里 0 次访问 C，只在最后读一次加一次 → 访存:计算降到 0.25:1。
每个载入的 `a` 被 8 列复用、每个 `b` 被 8 行复用，于是从「访存受限」翻转成「算力受限」。

> #### 📌 背景：寄存器 & 为什么 64 个累加器能塞进 32 个寄存器
>
> **NEON 寄存器 = ARM64 的向量/浮点寄存器 `v0`~`v31`，共 32 个，每个 128-bit。**
> NEON 是 ARM 的 SIMD 指令集，专门操作这组寄存器。ARM64 其实有两组寄存器：
>
> | 寄存器组 | 名字 | 数量 | 宽度 | 干什么 |
> |---|---|---|---|---|
> | 通用/整数（标量） | `x0`–`x30`（32 位视图 `w0`–`w30`） | 31 | 64-bit | 整数、**指针**、循环计数、地址 |
> | 向量/浮点（NEON） | `v0`–`v31` | 32 | 128-bit | SIMD 向量 **和** 标量浮点 |
>
> **有标量寄存器吗？** 有，分两种：
> - 整数/指针的标量 = `x0`–`x30`，独立一组（微内核里的指针、`k` 计数在这）。
> - 浮点的标量**没有单独一组**——它和 NEON 向量**共用 `v0`–`v31`**，只是用不同宽度「视图」看同一个物理寄存器：
>   `Qn`=128 位(4 个 float，向量) / `Dn`=64 位 / **`Sn`=32 位=一个标量 float** / `Hn`=16 位(fp16)。
>   例如 `naive_t` 里的累加器 `s` 就住在某个 `Sn`。AArch64 没有 x86 那种独立的标量 FPU 寄存器堆。
>
> **为什么 64 能放进 32？** 单位不同：**64 是「标量个数」，32 是「寄存器个数」**。
> 一个 NEON 寄存器装 **4 个 fp32**，所以 8×8=64 个累加器 ÷ 4 = **16 个寄存器**（不是 64 个）。
> 每行 8 个数 = 2 个寄存器（低半 4 列 + 高半 4 列），8 行 × 2 = 16：
>
> ```
>         列 0 1 2 3 | 列 4 5 6 7
>  行0    [  vreg0  ] [  vreg1  ]     ← 1 行 = 8 float = 2 个 float32x4
>  行1    [  vreg2  ] [  vreg3  ]
>   …          …           …
>  行7    [ vreg14  ] [ vreg15  ]
> 占用: 16 个装 C 累加器 + 4 个临时装 a0,a1,b0,b1 = 20 / 32, 还剩 12 个富余 ✓
> ```
>
> 反过来：若做 16×16=256 个累加器就要 64 个寄存器 > 32，会「寄存器溢出」到内存、微内核就废了。
> 所以微内核尺寸（8×8 / 8×12 …）本质上是**卡在「32 个向量寄存器」这条硬约束上**选出来的。

#### 把三步拼起来（`gemm_blocked_rows`）

打包不是免费的，所以要让打包好的数据被**大量复用**才划算——这就是外面几层分块的意义：
`MR=NR=8`（微内核尺寸）、`MC=KC=256`（让 A 微面板 + B 微面板留 L1、B 整条带留 L2）。

```
for pc in K step KC:            # 切 K 维
    pack B(pc.., 全部列)         # B 打包一次, 被下面所有行复用
    for ic in rows step MC:     # 切行
        pack A(ic.., pc..)       # A 打包一次, 被下面所有列微面板复用
        for jp in 列微面板(每8列):
            for ip in 行微面板(每8行):
                micro_8x8(...)   # 上面的三步: 累加 kc 步 → 回写 C 的 8×8 小块
```

> 📖 **变量太多看不清？** `gemm_v2` 的每个变量、每个下标算式、4 层循环怎么套、
> 三套坐标怎么对上，用一个 N=512 的具体例子逐行走了一遍：见 [`gemm_v2_详解.md`](gemm_v2_详解.md)。

### 3.4 v3 —— 多线程，打败 OpenMP

v2 已把单核压榨到 ~111 GFLOPS，再叠加多线程即可。策略最简单也最稳：
**按行条带切分**，每个线程负责 C 的一段不相交的行（以 8 行为粒度），
各自持有独立的打包缓冲区、独立跑一遍 v2 的分块内核，**无写冲突、无锁**。

```
14 个 std::thread，每个算 C 的 [r0,r1) 行 → join
```

B 会被每个线程各打包一份（冗余），但相对 O(N³) 的计算量可忽略。

### 3.5 cblas —— 厂商 BLAS 参考（真正的天花板）

`gemm_cblas` 直接调 Apple Accelerate 的 `cblas_sgemm`（标准 BLAS 接口，
`C = αAB + βC`，这里 α=1、β=0）：

```c
cblas_sgemm(CblasRowMajor, CblasNoTrans, CblasNoTrans,
            N, N, N, 1.f, A, N, B, N, 0.f, C, N);
```

**它的实现（黑盒但可推断）**：Accelerate 内部是一份高度调优的分块 GEMM，
和我们 v2/v3 的思路一致（打包 + 微内核 + 多级分块 + 多线程），但微内核跑在
**AMX（Apple Matrix Extension）矩阵协处理器** 上，而不是 NEON。
AMX 是每个 CPU 簇共享的专用矩阵引擎，做的是**外积累加**：一条指令就把一个
行向量 × 列向量 的外积加到一整块寄存器磁贴（tile）上，单位时钟的 FMA 数远超 128-bit NEON。

实测 **~3100 GFLOPS**（不随规模衰减），是 openmp 的 12×~16×（N 越大差越多，因为 openmp 掉速）、v3 的 ~3×。这说明：

- 我们用 NEON 手写到 v3（~850 GFLOPS）已经吃满了**通用 SIMD 流水线**；
- 但真正的天花板由**专用矩阵硬件（AMX）**决定，纯 intrinsics 够不到。
- 想再上一个数量级，得用 AMX/SME 指令，或者直接调厂商库——这也是工程上正确的选择：
  **GEMM 这种基础算子，生产环境就该用 BLAS。** 本项目的 v1→v3 是为了理解「优化是怎么发生的」。

### 各 kernel 的访存量（v2/v3 详细推导）

GEMM 共 `N³` 次乘加(madd)，共计 `2N³` flop。访存量 = 所有内层 load/store 发出的字节总数（不计 O(N²) 低阶项）。

**核心公式**：每个 madd 搬多少字节 × N³ = 总访存量。

#### naive（ijk）

每个 madd(`s += A[i][k]·B[k][j]`)：读 A(4B)、读 B(4B)。

> `8B/madd × N³ = 8N³ B`。N=2048 → ≈ 69 GB。

#### naive_t（转置 B）

和 naive 完全相同：读 A(4B)、读 Bᵀ(4B)。区别仅在 locality（Bᵀ 连续 → L2 命中），字节数不变。

> `8N³ B`。

#### ikj / openmp（改下标，无分块）

每个 madd(`C[i][j] += a·B[k][j]`)：**读 B(4B) + 读 C[i][j](4B) + 写 C[i][j](4B)**。`a` 被提到 j 循环外（不计入）。

> `12B/madd × N³ = 12N³ B`。N=2048 → ≈ 103 GB。

#### v2/v3（分块 + 打包 + 寄存器微内核）

从最内层 `micro_8x8` 往上逐层推导。**关键**：微内核的 K 维分块(KC=256) 决定一次 `micro_8x8` 跑 kc 步——每步 64B load，攒 kc 步后才**一次性读写 C 64 次（256B each way）**，C 的开销被 kc 摊薄。

**一次 `micro_8x8(kc)` 调用**：

```
kc 步 (p=0..kc-1):  每步 16 load → 64 B × kc
                             0 store（全在寄存器攒）
  最后回写 C:          读 C 64 个 float 256 B
                      写 C 64 个 float 256 B
                       合计 C 开销 = 512 B

→ kc 步总 load  = kc×64 + 256 B
  kc 步总 store =           256 B
  kc 步总 flop  = kc×128
```

以 `kc=256` 为例，每步摊到的访存 = `(kc×64+512)÷kc ≈ 64+2 = 66 B`（C 只占 ~2B/步）。

> **总访存量的推导**（v2 单线程）：
>
> 令 `MT = MC=256, KT = KC=256`（分块常数）。
>
> ```
>  总 micro_8x8 调用次数 = (N/KT) × (N/MT) × (N/NR) × (MT/MR)
>                        = N³ / (KT × NR × MR)
>                        = N³ / (256 × 8 × 8) = N³ / 16384
> 每次 micro_8x8 总访存 = kc × 64 + 512 ≈ KT × 64 = 16384 B(load) + 512 B(store)
> 全程序 load = (N³/16384) × KT × 64 = N³ × 64/64 = N³ B
> 全程序 store= (N³/16384) ×    512 = N³/32 B（低阶，可忽略）
> ```
>
> **v2 ≈ N³ B load + N³/32 B store ≈ 1.03 N³ B**；N=2048 → ≈ 8.8 GB。

对比表中每 madd 摊到的访存：

```
v2: (1.03N³ B) ÷ N³ madd ≈ 1.03 B/madd   → 访存:FMA = 1:1.94 ≈ 0.5
ikj: N³ madd × 12B/madd = 12N³ B          → 访存:FMA = 12:2 = 6:1
```

| kernel | 每 madd 字节 | 访存:FMA（翻 AI 方向） | 全程访存量 (主导项) | N=2048 |
|---|---|---|---|---|
| naive | 8 | 4:1 | 8N³ B | 69 GB |
| naive_t | 8 | 4:1 | 8N³ B | 69 GB |
| ikj/openmp | 12 | 6:1 | 12N³ B | 103 GB |
| v1 | ≥12 | ≥6:1 | >12N³ B | >103 GB |
| **v2/v3** | **≈1** | **≈0.5:1** | **≈N³ B** | **8.6 GB** |
| cblas | AMX tile (极低) | 极低 | ~N³ B | — |

> 推导验证：打包 (O(N²)) 忽略；C 回写 512B/调用 → 摊在 kc=256 上 ≈ 2B/步，计入上表（实际 ≈1.03N³，表中简记 N³）。
> ikj 的三项访存 log：`load B(4B) + load C(4B) + store C(4B) = 12B/madd = 12N³ B`。

**注**：上表算法用的 `B/madd`（每 madd 摊到字节数）把访存量和计算量直接对应；之前 `vs omp` 表是算 GFLOPS——不同口径，但 IK 越高的数字越快（详见 §4「算术强度」）。

**为什么 v3 能赢 3~4 倍？**

一句话：**openmp 是「访存受限」，v3 是「算力受限」。** 加速比不是靠更多线程堆出来的
（两者线程数一样、并行加速也都只有 ~8×），而是靠**单核内核质量**的代差。下面拆开讲。

#### (1) 关键指标：算术强度（每读一个字节能算多少次）

处理器的 FMA 单元每拍能吞很多次乘加，但数据得先从 cache/内存搬进寄存器。
决定性能的是 **算术强度 AI = flops / 搬运字节数**：AI 低 → 卡在访存带宽；AI 高 → 才能喂饱算力。

**openmp / ikj 的内层**（`C[i][j] += a * B[k][j]`）：

```
每次内层迭代:  1 次 FMA(=2 flops)   读 B[k][j] 4B  (+读写 C，C 常驻 cache)
```

每从 cache 载入一个 `B` 元素，**只用一次**就丢掉，没有任何寄存器级复用 →
AI ≈ 0.5 flop/byte。向量单元大部分时间在**等 load**，而不是在算。
即便自动向量化了，瓶颈也是 L1/L2 的 load 带宽，不是 FMA 吞吐。
这就是为什么单核 ikj 只有 ~32 GFLOPS——离峰值差得远，卡在访存。

**v2/v3 的 8×8 微内核**（`micro_8x8`）：内层每个 k 步

```
载入 8 个 A + 8 个 B  = 16 floats = 64 B
做  16 条向量 FMA     = 16 × 4 lane × 2 = 128 flops
```

AI ≈ 128/64 = **2 flop/byte，约 4 倍于 ikj**。更狠的是：8×8=64 个累加器**全程待在
NEON 寄存器里**（16 个 `float32x4_t`），整个 k 循环期间只在最后写回一次内存。
于是每载入 1 个 A 元素被 **8 列复用**、每个 B 元素被 **8 行复用**——
问题从「访存受限」翻转成「算力受限」，FMA 流水线被喂满。

| | 每步载入 | 每步 flops | 寄存器复用 | 瓶颈 |
|---|---|---|---|---|
| ikj / openmp | 4 B (B) | 2 | ~1× | **L1/L2 带宽** |
| v2 微内核 | 64 B | 128 | **8×** | **FMA 算力** |

#### (2) 打包 + 分块：让上面的理想值真正兑现

- **打包**（`pack_A`/`pack_B`）：把当前块重排成微内核**顺序连续**读取的布局，
  消除跨行 stride、让硬件预取生效、减少 TLB miss——否则 stride 访问会把上面的 AI 优势吃掉。
- **分块**（`MC=KC=256`）：让 A、B 的活跃微面板留在 **128KB 的 L1**、B 整条带留在 **16MB 共享 L2**，
  避免落到 DRAM。naive 的 B 列访问几乎每次 miss，就是反面教材（2 GFLOPS）。

单核效果：**v2 ≈ 110 GFLOPS vs ikj ≈ 32 GFLOPS，约 3.4×**。这就是「单核就把每字节内存的计算量拉高一个量级」。

#### (3) 多线程：把单核的代差原样放大

v3 与 openmp 都用 14 线程，但本机是 **10 性能核 + 4 能效核**（E 核更慢）+ 共享 L2/内存带宽，
所以两者的并行加速都只有 ~8×，而非 14×：

```
ikj  32  --×8.5 线程-->  openmp 274      (N=2048)
v2  110  --×7.9 线程-->  v3     865
```

**并行倍数两边几乎一样，胜负早在单核就分好了**：v2 对 ikj 的 ~3.4× 代差，
原样传递成 v3 对 openmp 的 ~3.16×（N=2048）。规模越大、openmp 越受带宽拖累，差距拉到 ~4×。

#### 一句话总结（Roofline 视角）

同一台机器、同样的算力/带宽屋顶下，**openmp 停在屋顶的低 AI（斜坡、访存受限）区，
v3 靠寄存器复用把 AI 推到高处、坐上了算力平台区**。差的那 3~4 倍，就是这段屋顶的高度差。

## 6. 还能更快的方向

- 更大/自适应的分块尺寸，双缓冲预取（`__builtin_prefetch`）隐藏打包延迟。
- 更宽的微内核（如 8×12 / 12×8）进一步提升寄存器复用。
- **走 AMX/SME 专用矩阵硬件**——这正是 cblas 快 ~3.6× 的原因；M4 支持 `SME2`，或直接用 Accelerate。
- bf16/fp16 降低访存、提升吞吐。
- 线程间共享 B 的打包结果，去掉冗余打包。
