# gemm_v2 逐行详解（把所有变量讲清楚）

v2 的代码变量多，是因为它有 **4 层循环 + 2 个打包缓冲区 + 3 套坐标系**。
本文用一个具体例子 **N=512** 把每个变量、每个下标算式都走一遍。

调用链：

```
gemm_v2( )                     ← 入口：分配缓冲、清零 C
   └─ gemm_blocked_rows( )     ← 4 层分块循环
         ├─ pack_B( )          ← 把 B 的一块揉成连续小条
         ├─ pack_A( )          ← 把 A 的一块揉成连续小条
         └─ micro_8x8( )       ← 真正算 8×8 小块（见 README §3.3）
```

---

## 0. 先记住三套坐标 + 一张变量表

矩阵都是 `N×N` row-major，元素 `M[i][j]` 存在 `M[i*N + j]`。

GEMM 有三个维度，先给它们固定的名字，后面所有变量都围着它们转：

```
        j / 列 (N)                 C[i][j] = Σ  A[i][k] * B[k][j]
       ┌──────────┐                          k
  i /  │          │        i = C 的行 = A 的行
  行   │    C     │        j = C 的列 = B 的列
 (N)   │          │        k = 累加维 = A 的列 = B 的行  (被求和消掉)
       └──────────┘
```

**变量总表**（N=512 时的具体值）：

| 变量 | 含义 | 属于哪个维度 | N=512 时 |
|---|---|---|---|
| `N` | 矩阵边长 | — | 512 |
| `MR` `NR` | 微内核尺寸（8×8） | i 方向 / j 方向 | 8, 8 |
| `MC` `KC` | 分块大小（一次处理多大一块） | i 方向 / k 方向 | 256, 256 |
| `pc` | **k 维**的分块游标（外层，切 K） | k | 0, 256 |
| `kc` | 当前 k 块的实际长度 = min(KC, N-pc) | k | 256 |
| `ic` | **i 维**的分块游标（切行） | i | 0, 256 |
| `mc` | 当前行块的实际高度 = min(MC, r1-ic) | i | 256 |
| `jp` | **列微面板**编号（每 8 列一个） | j | 0..63 |
| `ip` | **行微面板**编号（每 8 行一个） | i | 0..31 |
| `p` | 打包时在 k 块内的偏移（0..kc-1） | k | 0..255 |
| `r` | 微面板内的行偏移（0..MR-1） | i | 0..7 |
| `Apack` | A 的打包缓冲（MC×KC 大小） | — | 256×256 = 256KB |
| `Bpack` | B 的打包缓冲（KC×N 大小） | — | 256×512 = 512KB |
| `Ap` `Bp` | 指向 Apack/Bpack 里**某个微面板**的指针 | — | — |

> 关键区分：`MC/KC/MR/NR` 是**固定的块尺寸**；`pc/ic/jp/ip/p/r` 是**循环里动的游标**；
> `mc/kc` 是「这一块实际有多大」（边界不整除时会比 MC/KC 小，N=512 整除所以恒等于 256）。

### 从大到小：拆 pack 块

矩阵乘有三维：M(行)、N(列)、K(累加维)。分块策略只需要看**切不切**这三个维：

```
M 方向: 按 MC=256 切成行块，每块又按 MR=8 切成行微面板（全 M/8 个面板）
N 方向: 不设 NC（一次盖全部 N=512 列），按 NR=8 切成列微面板（512/8=64 个）
K 方向: 按 KC=256 切成 K 块
```

```
         N (512列, 按8切成64个列面板, 不切NC)
    ┌──────────────────────────────────────┐
 M  │ ┌────┐ ┌────┐        ┌────┐         │  ← MC=256 一个行块, 按 MR=8 切成 32 个行面板
 2  │ │8×8 │ │8×8 │  ...   │8×8 │         │
 5  │ │tile│ │tile│        │tile│         │
 6  │ └────┘ └────┘        └────┘         │
    │  ...                                │
    ├──────────────────────────────────────┤
    │              第二个行块               │
    └──────────────────────────────────────┘
```

### 微内核怎么在块上移动覆盖（4 层游标从大到小）

`gemm_blocked_rows` = **一把扫码枪**，用一个 K 段(pc)，把 C 的行区间[r0,r1)每个 8×8 tile 扫一遍，累加上这段 K 的贡献。

```c
for pc = 0, 256:             ← pc 在 K 维上跨 KC=256 移动 (K 分块)
  kc = 256
  pack_B()                          ← 打包 B 的这段 K(全部列)
  for ic = 0, 256:           ← ic 在 M 维上跨 MC=256 移动 (行分块)
    mc = 256
    pack_A()                        ← 打包 A 的这块 (ic..ic+255行 × pc..pc+255列)
    for jp = 0..63:          ← jp 在 N 维上跨 NR=8 移动 (列微面板)
      for ip = 0..31:        ← ip 在 M 维上跨 MR=8 移动 (行微面板)
        micro_8x8(kc, ...)         ← 算这个 [ip][jp] tile 在 [pc..pc+kc] 段的部分和
```

效果：两轮 `pc`(pc=0, pc=256) 扫同一个 tile，第一轮 `+=` 上一份 K 的部分和，第二轮 `+=` 把残补全——所以 C 须预清零、微内核用 `+=`。`pack_B` 仅每次 `pc` 做一次（下面所有行列复用），`pack_A` 每次 `ic` 做一次（该行下的所有列面板复用）。

## 1. `gemm_v2` —— 入口（3 件事）

```c
static void gemm_v2(int N, const float* A, const float* B, float* C) {
  std::memset(C, 0, (size_t)N*N*sizeof(float));   // ① C 全部清零
  const int MC = 256, KC = 256;                    // ② 定块大小
  float* Apack = alloc_f((size_t)MC * KC);         // ③ 分配打包缓冲
  float* Bpack = alloc_f((size_t)KC * N);
  gemm_blocked_rows(N, A, B, C, 0, N, Apack, Bpack, MC, KC);  // 算第 0..N 行
  free(Apack); free(Bpack);
}
```

- **① 为什么先清零 C？** 因为微内核是 `C += ...`（累加，不是赋值）。K 维被切成多块（`pc`），
  每块贡献一部分，累加到同一个 C 上，所以 C 必须从 0 开始。
- `0, N` 表示「算 C 的第 0 到 N 行」——v2 是单线程全算；v3 就是把这个 `[0,N)` 换成 `[r0,r1)` 分给多线程。

## 2. `gemm_blocked_rows` —— 4 层循环骨架

```c
for (int pc = 0; pc < N; pc += KC) {            // 【L1】切 K 维
    int kc = min(KC, N - pc);
    pack_B(N, B, pc, kc, Bpack);                //   打包 B 的这条 K 带（全部列）
    for (int ic = r0; ic < r1; ic += MC) {      // 【L2】切行
        int mc = min(MC, r1 - ic);
        pack_A(N, A, ic, mc, pc, kc, Apack);    //   打包 A 的这一块
        for (int jp = 0; jp < N/NR; ++jp) {     // 【L3】遍历列微面板(每8列)
            const float* Bp = Bpack + jp*kc*NR;
            for (int ip = 0; ip < mc/MR; ++ip) {// 【L4】遍历行微面板(每8行)
                const float* Ap = Apack + ip*kc*MR;
                micro_8x8(kc, Ap, Bp,
                          C + (ic+ip*MR)*N + jp*NR,  // 该 8×8 tile 在 C 里的左上角
                          N);
            }
        }
    }
}
```

N=512 时各层跑几次：

```
L1  pc  : 0, 256                → 2 次   (把 K=512 切成 2 段, 每段 kc=256)
L2  ic  : 0, 256                → 2 次   (把 512 行切成 2 块, 每块 mc=256)
L3  jp  : 0..63                 → 64 次  (512/8 个列微面板)
L4  ip  : 0..31                 → 32 次  (256/8 个行微面板)

micro_8x8 调用次数 = 2×2×64×32 = 8192 次
（= 4096 个 8×8 tile，每个被 2 段 K 各累加一次）
```

**为什么这样排？** —— 让打包的成本被最大复用：
- `pack_B` 在 L1 里，每段 K **打包一次**，被下面 L2/L3/L4 的所有行、所有列复用。
- `pack_A` 在 L2 里，每个行块 **打包一次**，被下面 L3 的所有列微面板复用。

## 3. `pack_B` —— 把 B 揉成「每个 k 一组连续 8 列」

```c
static void pack_B(int N, const float* B, int pc, int kc, float* Bpack) {
  int npanel = N / NR;                       // 64 个列微面板
  for (int jp = 0; jp < npanel; ++jp) {      // 第 jp 个面板 = 第 jp*8 .. jp*8+7 列
    float* dst = Bpack + (size_t)jp*kc*NR;   // 该面板在 Bpack 里的起点
    int jcol = jp * NR;                       // 这 8 列的起始列号
    for (int p = 0; p < kc; ++p) {            // k 块内第 p 行
      const float* src = B + (size_t)(pc+p)*N + jcol;
      vst1q_f32(dst + p*NR + 0, vld1q_f32(src + 0));  // 拷 8 个 float
      vst1q_f32(dst + p*NR + 4, vld1q_f32(src + 4));
    }
  }
}
```

布局公式：`Bpack[jp*(kc*8) + p*8 + c] = B[(pc+p)*N + jp*8 + c]`（c = 0..7 列内偏移）

图示（一个列面板 jp，内部按 p 一行行往下堆）：

```
 Bpack 里第 jp 个面板 (kc*8 个 float 连续):
   p=0 :  b(k=pc+0, 这8列)   ← 8 个 float
   p=1 :  b(k=pc+1, 这8列)
   ...
   p=kc-1: b(k=pc+kc-1, 这8列)
 → 微内核顺着往下读 (p=0,1,2,...)，每步刚好拿到「第 p 步要的 8 个列值」，0 stride。
```

**为什么要打包？** 原始 B 里，第 jp 面板的第 p 行和第 p+1 行相隔一整行(N 个 float)；
打包后它们**紧挨着**，微内核连续读、预取友好。

**具体例子**（N=16, pc=0, kc=3, 看面板 jp=1 管第 8..15 列）：

```
原始 B (行优先, 每行相隔 N=16):
   B[0][8..15]  在内存地址  8..15
   B[1][8..15]  在内存地址 24..31      ← 三行彼此隔 16, 不连续
   B[2][8..15]  在内存地址 40..47
pack_B 后 (面板 1, 24 个 float 连续):
   [ B[0][8..15] | B[1][8..15] | B[2][8..15] ]
     p=0 的 8 个    p=1 的 8 个    p=2 的 8 个
```

B 里「一行的 8 个连续列」本来就挨着，所以每个 p 用一条 `vld1q`(8 float) 直接搬——**纯拷贝，顺序不变**，只是去掉行间的 N-stride。

## 4. `pack_A` —— 把 A 揉成「每个 k 一组连续 8 行」

```c
static void pack_A(int N, const float* A, int ic, int mc, int pc, int kc, float* Apack) {
  int mpanel = mc / MR;                       // 行微面板个数
  for (int ip = 0; ip < mpanel; ++ip) {       // 第 ip 个面板 = 第 ic+ip*8 .. +7 行
    float* dst = Apack + (size_t)ip*kc*MR;
    int irow = ic + ip * MR;                   // 这 8 行的起始行号
    for (int p = 0; p < kc; ++p) {             // k 块内第 p 列
      int col = pc + p;
      for (int r = 0; r < MR; ++r)             // 8 行分别取一个
        dst[p*MR + r] = A[(size_t)(irow+r)*N + col];
    }
  }
}
```

布局公式：`Apack[ip*(kc*8) + p*8 + r] = A[(ic+ip*8+r)*N + (pc+p)]`

注意 A 这里是**转置着取**的：固定一个 k（列 `col`），把 8 行的值收集到一起。
原始 A 里这 8 个值是竖着排的（隔 N 个 float），打包后变成连续 8 个 → 微内核能一次性用。

**具体例子**（N=16, pc=0, kc=3, 看面板 ip=0 管第 0..7 行）：微内核第 p 步要「8 行在列 (pc+p) 上的值」

```
原始 A: p=0 步要的 8 个 = A[0][0], A[1][0], ..., A[7][0]
        它们在内存地址 0, 16, 32, ..., 112   ← 每个隔 N=16, 竖着排, 不连续!
pack_A 后 (面板 0):
   [ A[0][0]..A[7][0] | A[0][1]..A[7][1] | A[0][2]..A[7][2] ]
     p=0 的一列 8 行     p=1 的一列 8 行     p=2 的一列 8 行
```

因为这 8 个隔着 N、不连续，所以用标量 `for r` 逐个 gather，等于把 `8 行 × kc 列` 的块**转置**成 `kc × 8`。

### 4.5 pack_A 和 pack_B 差在哪？（一个转置、一个纯拷贝）

两个打包函数产出的**目标布局一样**（都是「kc 组、每组 8 个连续数」喂给微内核），
差别只在**源数据要不要重排**。微内核每个 k 步要：A 的 **8 个行**在该 k 上的值、B 的 **8 个列**在该 k 上的值。
在行优先(`M[i][j]` 存 `i*N+j`)下看这 8 个数连不连续：

| | 微内核要的 8 个 | 地址 | 连续？ | 打包动作 |
|---|---|---|---|---|
| **B** | 一行的 8 个**列** | `k*N + (j0+c)`, c=0..7 → 每 +1 列地址 +1 | **连续** ✓ | **直接拷贝**(`vld1q`/`vst1q`) |
| **A** | 一列的 8 个**行** | `(i0+r)*N + k`, r=0..7 → 每 +1 行地址 +N | **跨 stride** ✗ | **转置 / gather** |

小例子（用 2×2 微内核、kc=3）：

```
A 块(2行×3列) 内存: [a00 a01 a02 | a10 a11 a12]
pack_A 要:           a00 a10 | a01 a11 | a02 a12   ← 顺序变了 = 转置(2×3→3×2), a00,a10 隔 N 取
B 块(3行×2列) 内存: [b00 b01 | b10 b11 | b20 b21]
pack_B 要:           b00 b01 | b10 b11 | b20 b21   ← 顺序没变 = 纯拷贝, 只去掉行间 N-stride
```

### 4.6 「naive 里 A 明明是连续的，怎么 pack 又要转置了？」

不矛盾——**「连不连续」不是 A/B 的固有属性，而是取决于「沿哪个下标在动」**。naive 和微内核动的轴不同：

```
naive ijk 内层沿 k 扫:
  A[i][k]  地址 i*N+k  → k+1 地址+1   连续 ✓   ← naive 说"A 连续"是这个意思(沿 k 流式)
  B[k][j]  地址 k*N+j  → k+1 地址+N   跨N ✗

微内核每个 k 步, 沿"8 行/8 列"方向抓一批:
  A 的 8 行  地址 (i0+r)*N+k → r+1 地址+N   跨N ✗   ← pack 说"A 要转置"是这个意思(固定 k 跨 8 行 gather)
  B 的 8 列  地址 k*N+(j0+c) → c+1 地址+1   连续 ✓
```

同一个 A：naive 沿 **k**（一行内）读它 → 连续；微内核在固定 k 上沿 **i**（跨 8 行）读它 → 跨 stride。
两个不同的轴，所以结论「反过来」了。根因是**寄存器分块**：微内核一次算 8 行×8 列的 tile，
被迫在每个 k 步同时凑齐「A 的 8 行 + B 的 8 列」，而「A 的 8 行」正好是跨 N 的方向 → 必须转置。

> 这也说明：谁需要转置取决于**源矩阵存储序**。若 A 改成列优先存储，就变成 pack_A 拷贝、pack_B 转置了。

### 4.7 pack_A 为什么「跳着读、顺着写」，而不是反过来？

pack_A 的代码是「读 A 跳 N、写 dst 连续」。有人会问：为什么不「顺着读一整行 A、跳着写 dst」？三点：

**(1) 这是转置，必然有一边跳。** `Apack` 的布局被微内核规定死（k-major），源 A 是行优先(i-major)，
i-major→k-major 就是转置——转置的数学性质决定**读和写不可能同时连续**，你捋顺一边、另一边必跳。
「顺读跳写」和「跳读顺写」产出的 `Apack` **完全相同**，只是把「跳」从写挪到读，不影响正确性。

```
现在(跳读顺写):  for p: for r:  dst[p*8+r] = A[(irow+r)*N + col]   读跳 N / 写连续
另一种(顺读跳写): for r: for p:  dst[p*8+r] = A[(irow+r)*N + pc+p] 读连续 / 写跳 8
```

**(2) 选「写连续」是因为散写比散读更亏。** 写连续 → `dst` 一路填满整条 cache line，
store buffer/write-combining 舒服；若「跳着写」(stride 32B) → 每条 line 只写一部分(partial-line write)，
可能触发 read-modify-write，更慢。而跳读那侧因为块小(MC×KC)、8 行的 cache line 会在相邻 p 里被接着用满，并不浪费。

**(3) 转置只在打包时付一次。** `pack_A` 每个块只跑 1 次，而微内核读 `Apack` 要跑成千上万次
（(N/8)²×(K/KC)）。**把转置的跳跃成本一次性付在打包里，换热点微内核全程 0-stride 顺序读**——
这才是打包的核心哲学。选 (1)/(2) 只是这「一次」内部的小优化。

#### 实测验证：两个版本直接 benchmark

拆开 pack_A 的两个等价实现（跳读顺写 vs 顺读跳写），单次打包耗时（`MC=256`, `KC=256` 时 KC=min(256,N)）：

| N=128 KC=128 | strided_load=8.2 µs | strided_store=**7.4 µs** | store 略快 |
|---|---|---|---|
| N=256 KC=256 | **7.3 µs** | 16.0 µs | load 快 2.2× |
| N=512 KC=256 | **6.7 µs** | 16.5 µs | load 快 2.5× |
| N=1024 KC=256 | **6.3 µs** | 16.3 µs | load 快 2.6× |
| N=2048 KC=256 | **5.8 µs** | 16.4 µs | load 快 2.8× |
| N=4096 KC=256 | **5.7 µs** | 14.8 µs | load 快 2.6× |

结论：**KC≥256（实际使用范围）跳读顺写稳赢 2.5–3×**。N=128/KC=128 时跳写略快，
是因为 mc×KC=256×128 的 8 行面板总共才 4KB、cache 装得住且 partial-line 代价小，
但实际 GEMM 从不跑这种小区块。所以当前代码选的**跳读顺写是正确的**。

> 通用法则：**读可以乱序（MLP 藏延迟 + 预取 + 乱序执行），写成该顺序（partial-line write + store buffer/有序提交）。** 这也是转置/打包代码的经验手册，实测支撑的。

#### 硬件层面：为什么 load 能乱飞、store 不能？

##### 1. Load queue 为什么大、Store buffer 为什么小？

两者大小差 ~2x（M4 P-core: load≈200、store≈100），但根因不一样——是**投机性 + 回滚 + 探测**在起作用。

|  | load | store |
|---|---|---|
| 什么时候发射 | **提前**(投机) | **退休时**(非投机) |
| 错了怎么办 | **flush** 重来 | **不可回滚** |
| 每条 load/store 的附加负担 | 无 | **全相联搜索**：每发一条 load，必须查 store buffer 做 `store→load forwarding` |
| → 队列大小 | **大** | **小**（查起来太贵，不能太大） |

- **load 可以投机**：一条 load 可以被发射到「前边分支结果还不知道、store 地址也未知」的状态——猜中了就快、猜错了 flush 重来。所以 load queue 必须大（多装、多飞）。
- **store 不能反悔**：store 写进 L1 就回不去了，只能等指令确认非投机（退休）后再提交。而且每条新 load 必须**全相联查一遍 store buffer**（这个 load 的地址刚被前面某个未提交的 store 改过吗？）——这是一个 1-port 的热路径搜索，store buffer 每增大 1 条，面积/功耗/延迟都涨，所以特意**做不大**。

##### 2. MSHR / MLP：能同时 miss 几条 load？

**下列资源全部是单核级别的**（每个 P-core 自己有一套，和别的核无关）：L1 cache、load queue、store buffer、MSHR、fill buffer、预取器。只有 L2 是 P-core 簇内共享的。

记忆层次（一个 P-core）：

```
用户指令: ldr x0, [x1]
          ↓
    ┌─ Load Queue (~200 条, 放发出但未完成的 load)
    │
    ├─ L1D (128KB, 查找命中/miss)
    │   │
    │   ├─ 命中 → 数据返回, load 从 queue 里退休
    │   │
    │   └─ miss → 分配 MSHR 槽位 (硬上限, ~12-16 条, 用它跟踪"正在往 L2 发请求")
    │              ↕ 满了就不能再 miss —— 这就是 MLP 的硬天花板
    │         → Fill Buffer (~8-16 条, 槽位存放"L2→L1 正在来的 cache line")
    │              ↕ Fill buffer 满了就暂停发出新的 miss 请求
    │         → L2 (16MB 共享) → 如果 L2 也 miss → DRAM
    │
    └─ Store Buffer (~100 条, 放未退休的 store, 退休后逐条往 L1 写)
       也做 store→load forwarding (load 查到此 buffer)
```

三条硬死线决定 MLP（同一时刻 cache miss 中的 load 数上限）：

| 资源 | 在哪里 | 作用 | 单核数量 | 决定什么 |
|---|---|---|---|---|
| **MSHR** | L1D 内部 | 每条 cache miss 占 1 个槽，追踪「这份数据向 L2/DRAM 请求了」 | ~12-16 | MLP 硬天花板 |
| **Fill Buffer** | L1↔L2 之间 | 正在从 L2 搬到 L1 的 cache line 槽位 | ~8-16 | MLP 第二天花板 |
| **Load Queue** | 核心前端 | 已发出但未完成的 load 指令 | ~200 | 能同时「飞多少条」（含排队等 MSHR 的） |

**不同厂商选型差异**（2023-2025 gen，均单核）：

| | MSHR (L1) | L1→L2 fill buffers | load queue | 哲学 |
|---|---|---|---|---|
| Apple M4 P-core | ~12-16 | ~8-16 | ~200 | **中等 MSHR + 极强预取器**（把 miss 变命中）|
| Intel Golden Cove | ~48 | ~32 | 192 | **高 MSHR**（对随机访问 MLP 激进，靠硬扛） |
| AMD Zen5 | ~24 | ~16 | 88 | 折中 |

##### 3. 这对 pack_A 意味着什么？

Apple 的哲学是「预取 > 硬扛 miss」。pack_A 的 `for r: A[(irow+r)*N + col]` 是 8 流 strided load（每条流 stride=N×4），预取器看见规律就能提前搬 cache line。KC=4096/N=4096 时跳读顺写 5.7µs vs 跳写顺读 14.8µs（3×），正是因为**预取器几乎全把跳读 miss 吃掉了**，而跳写那侧 partial-line write 没有预取器能救——write 只能在退休时提交、一条条硬碰 store buffer + write combining，该亏还是亏。

所以答案：**「读可乱序、写要顺」不只是一个软件口号——底层硬件对 load/store 的整套机制（投机、不分回滚、port 不对称、store→load forwarding 成本、可预取性）是偏向 load 的**。用硬件的非对称性选择对应的算法（跳读顺写），这就是所谓的「cache-aware/memory-level-aware」优化。

#### 4.8 Load Queue 的 200 条里装的什么？为什么常规服务打不满？

Load Queue 存的不是「200 条 DRAM miss」，而是**所有已发射但未退休的 load——不管它现在在哪个阶段**。一条 load 的生命周期和它在 queue 里的占位：

```
Issue → Addr Gen → L1 lookup ─┬─ 命中  → 数据回来 → Wake consumer → Retire
          (1-2clk)   (4-5clk)  │
                                └─ miss → 抢 MSHR → 发 L2 → 等 DRAM(300+clk)
```

200 条的构成（实际占比）：

| 约占比 | 状态 |
|---|---|
| ~20% | 地址还没算完（在等前面的 pointer 寄存器的值就绪） |
| ~50% | L1 命中了，数据马上回来 |
| ~20% | L1 miss、在等 L2 fill（fill buffer 占着） |
| **~<10%** | **DRAM miss、在飞（MSHR 同时最多 12–16 条）** |

**关键**：Load Queue ≈ 登机大厅（能挤 200 人），MSHR ≈ 安检口（同时只能过 ~12 人）。大厅里大部分人只是正常走路/等同伴（=命中/排队），不需要过安检。只有那 ~12 条真的在 DRAM 上飞着。

**什么场景能打满？** 高 IPC + 高 load 密度 + 长缓存延迟 的组合（极端计算密集+访存混合）。**常规线上服务（Web、RPC、数据库）几乎不可能有节奏地打满 200 条**——IPC 远低于峰值，load 密度也不够。200 不是「日常用满」，是**设计余量**，比「满」多几倍，才能在极端情况下不成为瓶颈。GEMM 相关的：

| kernel | 能拉满 Load Queue？ |
|---|---|
| naive/ikj/openmp | 不能（load 串着等，IPC 低，大量时间在等） |
| v2/v3 微内核 | **有可能靠边，但实际不会满**（L2 命中率极高、MSHR miss 数少；load queue 在 50–100 条占用） |

#### 4.9 MSHR 12–16 是单核的，128 核服务器  DRAM 扛得住吗？

MSHR 决定的是**单核**同时能 miss 几条；服务器级看的是**全系统 DRAM 能扛几条同时 in-flight 请求**。

AMD EPYC 9654 (Zen 4, 12 通道 DDR5-4800, 128 核)：

| 层级 | 最大并发请求数 |
|---|---|
| 单通道 DDR5 | 32–64 条（rank × bank-group 交错极限） |
| 单根内存条（dual-rank） | ~128 条 |
| 12 通道全系统 | **~1000–1500 条** in-flight 请求 |
| 128 核 × 每条 12 MSHR = **2048 条**理论请求 | 🚫 **DRAM 扛不住** |

**结论**：高核心数时真正的 MLP 上限不是单核 MSHR，而是**内存控制器/DRAM 侧的排队深度和带宽**。芯片内请求聚合器（Coherent Slave/Data Fabric）在内存控制器前排队——超过 ~1000–1500 条并发后，额外请求只能等在 memory controller queue 里。GEMM 在服务器上调分块大小时，要同时考虑 K/N 的规模和全核数，避免全核同时 miss 争抢内存带宽——否则每个核的 MSHR 再多也是白占。

#### 4.10 类比总结（登机大厅 vs 安检口）

```
        Load Queue (200 条)              MSHR (12-16 条)
   ┌────────────────────────┐    ┌───────────────────┐
   │  ★ 地址还没算完       │    │  ★ DRAM miss 的 12 |
   │  ★ L1命中, 等数据回来 │    │    条在飞, 每条约  │
   │  ★ L1 miss, 等 L2 fill│    │    200-400 周期后  │
   │  ★ DRAM miss, 排队中  │    │    才返回          │
   └───────────┬────────────┘    └─────────┬─────────┘
               │                           │
      登机大厅 (过客、等同伴、    安检口 (同时只能
      在办登机、找座…)           过 12 人, 一个一个来)
      能挤 200 人                最多 12 人同时检
```

所以 load queue 的深度 = M4 的 ROB 窗口（600–700 条指令），load 占比 ~1/3 → 约 200 条。**不是为 DRAM miss 设计的，是为乱序窗口广，把大量命中的 load 也兜住。**

## 5. `micro_8x8` 的指针 —— 三套坐标怎么对上

回到 L4，一次微内核调用：

```c
micro_8x8(kc,
          Ap = Apack + ip*kc*MR,          // 第 ip 个行微面板
          Bp = Bpack + jp*kc*NR,          // 第 jp 个列微面板
          C + (ic + ip*MR)*N + jp*NR,     // C 里这个 8×8 tile 的左上角元素地址
          N);                              // ldc = C 的行跨度 = N
```

- `Ap` 提供「8 行 × kc」的 A 条；`Bp` 提供「kc × 8 列」的 B 条。
- 微内核内部循环 `p = 0..kc-1`，每步做 8×8 外积累加（README §3.3 那三张图），
  最后把 8×8 结果 `+=` 回 C 的 `[ic+ip*8 .. +7]` 行、`[jp*8 .. +7]` 列。

---

## 6. 完整追踪一个 tile（把上面全串起来）

设 `pc=0`(kc=256)、`ic=0`(mc=256)、`jp=3`、`ip=5`：

```
行范围 = ic + ip*8 .. +7 = 0 + 40 .. 47   → C 的第 40..47 行
列范围 = jp*8 .. +7       = 24 .. 31       → C 的第 24..31 列
Ap 指向 Apack 第 5 个行面板 = A[40..47][0..255]  (已打包)
Bp 指向 Bpack 第 3 个列面板 = B[0..255][24..31]  (已打包)

micro_8x8 累加 p=0..255:
    C[40..47][24..31] +=  Σ(k=0..255)  A[40..47][k] * B[k][24..31]

然后 L1 进入 pc=256 (kc=256)，同一个 tile 再来一次:
    C[40..47][24..31] +=  Σ(k=256..511) A[40..47][k] * B[k][24..31]

两段 K 加完 → C[40..47][24..31] = 完整的 Σ(k=0..511)  ✓
```

这就是为什么 **C 要先清零、微内核用 `+=`**：一个 tile 的最终值是被 L1 的多段 K **分次累加**出来的。

## 7. 常见疑问速查

| 疑问 | 答案 |
|---|---|
| `kc` 和 `KC` 区别？ | `KC` 是设定的块大小(256)；`kc` 是这一块**实际**长度，末尾不整除时更小。`mc/MC` 同理。 |
| 为什么 B 每段 K 都重打包？ | `Bpack` 只存一段 K(KC×N=512KB)，放得进 cache；下一段 pc 覆盖它。用空间换复用。 |
| `Bpack` 为何是 KC×N，`Apack` 是 MC×KC？ | B 要一次覆盖**全部 N 列**（被所有行复用）；A 只覆盖当前 MC 行块。 |
| 三套坐标？ | ①原矩阵行列(i,j,k) ②分块游标(pc,ic,jp,ip) ③面板内偏移(p,r,c)。下标算式就是在这三者间换算。 |
| N 不是 8 的倍数怎么办？ | 当前 demo 要求 N%8==0（benchmark 尺寸都满足）；通用实现需对边角 tile 补零，见 README §6。 |
| v2 和 v3 差别？ | 仅入口：v2 调 `gemm_blocked_rows(...,0,N,...)` 全算；v3 把 `[0,N)` 按 8 行粒度切给多线程，各带自己的 Apack/Bpack。 |

配合 README §3.3 的三张图（打包→累加→回写）一起看，整个 v2 就通了。
